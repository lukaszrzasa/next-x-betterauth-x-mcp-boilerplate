# Localization happens at the boundary, not in handlers

The application serves two languages, English and Polish, and a product built from it may serve one or both: `appConfig.locales` in `src/lib/config.ts` is the only knob. There is no language switcher and no stored preference. The proxy negotiates a request's locale once (an explicit `locale` cookie, then the browser's `Accept-Language`, then the default) and hands it to the app as the `x-locale` request header, always overwritten so a client-supplied value never gets through. Everything downstream reads that header through `requestLocale`: next-intl's request config for pages and components, the action adapters, the Better Auth hook and the provider-request context for emails. A single-language product narrows the list and negotiation becomes a no-op.

Operations, services and persistence never pick a language. A refusal names what went wrong as a catalog key with its values (`new ActionError("CONFLICT", { message: { key: "auth.errors.requestExpired" } })`), and the adapter that answers the caller renders it in the request's locale. The client contract is unchanged: `error.message` is a sentence. An error carrying only a developer string answers with the generic sentence for its reason; the string stays in the server log. Better Auth's own endpoints get the same treatment in one `after` hook that rewrites the provider's English message by its stable `code`, so the sign-in forms never show the provider's words. Zod schemas stay plain values shared by the client form and the server operation: a custom message is a catalog key, and both the form resolver and the server's input parsing translate issues the same way, with Zod's locale pack for the built-in messages.

Catalogs follow the module scopes. Each `_` keeps its messages next to its code (`app/(AuthModule)/_/messages/{en,pl}.json`, likewise the admin scope, the logs module and `src/lib/email`), and `src/lib/app/messages` composes them under one namespace per scope, which is the cross-module composition `src/lib/app` already does for navigation. English is the source of truth: the key types are generated from it, so a key that does not exist fails to compile, and a locale missing a key falls back to English at runtime rather than rendering the key. A test keeps every locale's key tree identical and every message valid ICU, so the fallback is never needed.

Written records stay as written. A staff log entry is a snapshot in the language it was written in (ADR 0003), and the email log keeps the subject and text that were sent; only `date` blocks render in the reader's locale. Every instant is shown in UTC with the zone named, in the request's locale, through one set of named presets; timezone negotiation is a separate feature.

The alternatives were a `[lang]` path prefix, per-user locale columns and a switcher, translating on the client from reason codes, and a community plugin for the provider's messages. The prefix would nest every route group and the root layout under a segment that client components, server actions and route handlers cannot read, for an app that is signed-in and has no SEO surface. Columns and a switcher are a product decision this template leaves open; the resolver has the slot for a stored preference when one exists. Client-side translation from reasons would have left every surface that is not a browser - a route handler, a future MCP tool - with English or with its own mapping. The plugin would have brought another author's Polish and two unused peer packages for twenty lines of hook. A lint rule against string literals in JSX was considered and deferred: the rules available flag `aria-*`, class names and punctuation faster than they flag copy, so new hardcoded text is caught in review for now.
